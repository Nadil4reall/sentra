# SENTRA M6A controller-agent architecture

## Status and scope

Milestones 1–5 are complete at their documented Proof-of-Concept scope. M6A adds the
protocol, identity, persistence, and controller/agent skeleton needed to begin managing
more than one Ubuntu target centrally. It does not replace or change the M3 profiler,
M4 compatibility engine, or M5 sandbox validator.

M6A is an in-process implementation and test boundary. No real Mac-to-Ubuntu network
transport or TLS exchange has been validated, and no VM was contacted during its
implementation. It provides no remediation, deployment, arbitrary command execution,
sandbox lifecycle automation, approval workflow, or dashboard.

The Mac and Ubuntu VMs used by the research project are temporary lab roles. Their IP
addresses, hostnames, usernames, and other VM-specific values are not product
identities, protocol defaults, or assumptions in this design.

## Agent-initiated trust boundary

All target communication is initiated outbound by the Agent:

```text
Agent                                 Controller
  |--- ENROLL -------------------------->|
  |<-- target/agent IDs + credential ----|
  |--- HEARTBEAT ------------------------>|
  |--- POLL_JOB ------------------------>|
  |<-- PROFILE_TARGET or no work --------|
  |--- SUBMIT_PROFILE ------------------->|
```

The Controller never SSHs into a target. The protocol has no `RUN_COMMAND`,
`RUN_SHELL`, `EXEC`, command-string, generic argv, or equivalent remote execution
facility. The only M6A operational job type is `PROFILE_TARGET`; unknown and
command-like job types are rejected rather than passed through.

The current Agent-side profile operation is a protocol boundary for future reuse of
`src/target_profiler/`. M6A does not yet run the real M3 profiler on a VM. Similarly,
the Controller records the lineage interface needed by a future M4 orchestration phase
without invoking `src/compatibility_engine/` in M6A.

## Identity model

| Identity | Issuer and lifetime | Security meaning |
|---|---|---|
| `target_id` | Opaque UUID generated by the Controller at enrollment | Authoritative SENTRA identity for the managed target; not derived from an address or hostname |
| `agent_id` | Opaque UUID generated by the Controller at enrollment | Authoritative identity for one enrolled Agent and the credential bound to it |
| `installation_id` | Opaque UUID generated locally by the Agent on first initialization and persisted across normal restarts | Correlates one Agent installation during enrollment and restart; it is not authority to select a target |

Observed hostname, operating system, OS version, kernel, and architecture are metadata,
not identity. The Controller may record changes to those observations, but an observed
hostname or address cannot rename a target, claim another target's jobs, or authorize a
profile submission.

Raw `/etc/machine-id` is neither sent nor stored as a SENTRA identifier. The M6A schema
permits an optional SHA-256-shaped value solely as non-authoritative correlation
evidence, but the Agent skeleton does not collect or generate it. Before a later phase
derives such evidence, it must define a purpose-specific privacy and derivation policy,
including whether a salt or keyed hash is needed to prevent unintended correlation.

## Enrollment and authentication

Initial enrollment is the only operation authorized by the configured bootstrap
credential. A successful enrollment returns:

- Controller-issued `target_id` and `agent_id`;
- a per-Agent credential; and
- Controller settings such as the polling interval.

The Agent persists its `installation_id` and enrollment state for reuse across normal
restarts. Its state path is caller-configured rather than host-specific. The state and
atomic temporary files use mode `0600`; unsafe symlinks, non-regular destinations,
symlinked parents, and incorrectly permissioned existing state are refused. An existing
enrollment cannot be rebound to different Controller identities or credentials.

After enrollment, heartbeat, job polling, and profile submission use the per-Agent
identity and credential, not the bootstrap credential. The Controller binds that
authenticated Agent to one `target_id`; caller-supplied identifiers cannot be used to
impersonate another target or access its jobs and profiles.

Plaintext credentials are secret values. They must not appear in ordinary model
representations or logs. Controller persistence stores credential verification
material rather than a recoverable plaintext credential; the issued per-Agent secret
is returned only as enrollment output for Agent-side storage.

M6A tests may call the service in-process. A later real-network phase must require TLS
and Controller certificate or CA verification. Plaintext HTTP carrying bearer
credentials is not an accepted deployment architecture.

## Protocol operations

| Operation | Authentication | M6A responsibility |
|---|---|---|
| `ENROLL` | Bootstrap credential | Register an installation, create Controller identities, and issue a per-Agent credential |
| `HEARTBEAT` | Per-Agent credential | Update `last_seen`, status, Agent version, and appropriate observed metadata |
| `POLL_JOB` | Per-Agent credential | Return only that Agent's target-scoped pending `PROFILE_TARGET` work |
| `PROFILE_TARGET` | Dispatched job | Represent the single allowlisted operational action; future implementation will invoke M3 through a narrow interface |
| `SUBMIT_PROFILE` | Per-Agent credential | Accept a result only for the authenticated Agent's own target and job, compute the authoritative canonical-evidence hash, and record lineage |

There are no remediation or deployment operations in this protocol.

### Conceptual `/api/v1` mapping

M6A records the following versioned endpoint-shaped mapping in `ControllerAPI`:

| Method and path | Purpose |
|---|---|
| `POST /api/v1/enrollment` | Bootstrap enrollment |
| `POST /api/v1/agents/{agent_id}/heartbeat` | Authenticated Agent heartbeat |
| `POST /api/v1/agents/{agent_id}/jobs/poll` | Poll the authenticated Agent's own pending job |
| `POST /api/v1/agents/{agent_id}/profiles` | Submit profile evidence for the authenticated Agent's dispatched job |
| `GET /api/v1/admin/targets` | List registered targets through the authenticated Controller/admin boundary |
| `POST /api/v1/admin/targets/{target_id}/jobs` | Create an allowlisted `PROFILE_TARGET` job |

These are protocol concepts, not a claim that a production HTTP server, admin
authentication scheme, or real network listener exists in M6A. No remediation,
deployment, shell, or generic command endpoint is planned under this namespace.

## Profile evidence and lineage

Accepted profile evidence is associated with:

```text
target_id -> agent_id -> job_id -> profile_id
```

The profile record retains `collected_at`, Controller `received_at`, available
SENTRA/profiler version information, and a SHA-256 of the validated profile's canonical
JSON representation. The Controller calculates this authoritative evidence hash; an
Agent-supplied digest is not treated as authority. Target/job ownership is checked
before storage, so one Agent cannot overwrite or submit evidence for another target.

The M3 evidence meanings remain unchanged at this boundary:

- `collected`
- `unavailable`
- `unsupported`
- `error`

M6A must not collapse non-collected states to `false` or reinterpret profile facts as
compatibility or compliance conclusions.

Future M4 orchestration extends the lineage without changing those semantics:

```text
target_id -> profile_id -> compatibility_report_id
```

A compatibility record must identify the target and source profile, benchmark identity
and version, generation time, and report SHA-256. Current research remains scoped to
the CIS Ubuntu Linux 24.04 LTS Benchmark v1.0.0. Licensed CIS-derived source data stays
separate from SENTRA-derived metadata, safety logic, and implementation choices; each
SENTRA interpretation must retain a documentable rationale.

## Persistence boundary

M6A uses Python standard-library SQLite behind `ControllerRepository`, with
`SQLiteControllerRepository` as the local implementation suitable for a multi-target
PoC. `ControllerService` owns authenticated protocol operations, and `ControllerAPI`
adds the versioned endpoint-shaped identity-binding facade. The storage boundary covers
targets, Agents and credential verification, jobs, profiles, and future
compatibility-lineage records. Services depend on repository operations rather than
issuing persistence-specific queries throughout the protocol layer, leaving room to
replace the PoC store later.

The repository reserves `data/controller/` and `data/agent/` for project-local runtime
artifacts; generated Controller databases, Agent credentials, and runtime state there
remain Git-ignored. Runtime paths are still supplied by the caller. SQLite is not
presented as the final production topology, and M6A does not introduce PostgreSQL or
other enterprise infrastructure.

## Current and planned work

### Current

- M1–M5 are complete at their documented PoC scope.
- M6A defines and tests the controller/agent protocol skeleton, persistent identities,
  enrollment and per-Agent authentication, target-isolated jobs, SQLite repository
  boundary, and profile evidence lineage.

### Planned later

- execute the existing M3 profiler through the Agent's `PROFILE_TARGET` adapter;
- orchestrate the existing M4 compatibility engine on the Controller with recorded
  profile-to-report lineage;
- implement and validate TLS transport on a real Agent-to-Controller network;
- design deployment and approval workflows without adding arbitrary remote execution;
- implement the sandbox manager and external snapshot integration; and
- build the dashboard and central audit presentation.

The next M6B step is the first real, TLS-verified Agent-to-Controller integration using
the narrow `PROFILE_TARGET` path and existing M3 profiler, while preserving target
isolation and the absence of a generic command channel.

## Security limitations still open

- M6A has not validated network transport, certificate provisioning, rotation,
  revocation, replay protection, rate limiting, or recovery from lost Agent secrets.
- Bootstrap and per-Agent secret provisioning remain deployment concerns; credentials
  must not be embedded in source control or command logs.
- The PoC Agent state protects its bearer credential with local path checks and mode
  `0600`, not an operating-system keychain or hardware-backed secret store.
- Controller/admin authorization is only an interface boundary in M6A.
- SQLite provides local PoC persistence, not a high-availability or hardened
  production database; Controller database permissions, encryption at rest, backup,
  and recovery are deployment responsibilities.
- M6A does not prove the trustworthiness of target-provided observed metadata or
  profile evidence; it proves authenticated ownership and records evidence lineage.
- Deployment approval, sandbox lifecycle, remediation verification, broader control
  coverage, and dashboard/audit workflows remain future work.
